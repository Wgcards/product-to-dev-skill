# Internationalization

## Default Setup

- New React projects must include `i18next` and `react-i18next`.
- Put i18n setup and dictionaries under `src/locale/`.
- Default dictionaries:
  - `src/locale/zh-CN.json`
  - `src/locale/en-US.json`
- Treat `zh-CN` as the human-maintained source language unless the user says otherwise.

## What Goes Into Locale Files

- Page titles, menu labels, buttons, table headers, status labels, filter labels, form labels, validation messages, empty states, and Snackbar text.
- Frontend-generated copy must be localized.
- Frontend-generated copy includes page content, buttons, labels, placeholders, aria labels, titles, loading text, empty states, error states, validation messages, Snackbar/Dialog text, APIClient fallback errors, request-wrapper fallback `codeMsg`, helper-generated display text, and mock fixture display copy.
- Backend `codeMsg` can be displayed directly and does not need frontend translation when backend i18n is part of the API contract. This exception does not apply to frontend-generated `codeMsg` or fallback messages.

## Hard Rules

- Do not hardcode user-visible copy in TS/TSX/Vue/JSX/JS files.
- This applies to pages, components, hooks, services, request wrappers, APIClient, helpers, stores, constants, and mock fixtures.
- Allowed hardcoded exceptions are brand names, product names, third-party proper nouns, protocol values, enum keys, CSS class names, comments, logs, and test descriptions.
- APIClient and request wrappers should prefer stable error codes plus locale-backed messages. If they generate `codeMsg`, that message must come from the shared i18n instance or an equivalent locale-backed source.
- Hooks and components should translate fallback copy at the UI/orchestration boundary. They may pass translated messages into lower-level hooks instead of letting lower-level code import i18n directly.
- Mock fixtures that represent user-visible content must be locale-aware. Use locale dictionaries, per-locale examples, or a documented API/CMS contract that returns content in the requested language.
- OpenAPI/API examples may contain backend-returned localized `codeMsg`, but frontend fallback behavior must still be covered by locale files.

## Sync Rules

- Treat one locale file as the only human-maintained source, usually `src/locale/zh-CN.json`.
- Confirm target languages before translating unless the user already specified them.
- If the source locale is not specified, inspect the repository and default to `zh-CN.json` or `zh_CN.json` only when such a Chinese source file clearly exists.
- If no clear Chinese source locale file exists, stop and ask the user before continuing.
- Inspect the locale file format, then compare source and target dictionaries by flattened ordered key paths.
- Translate leaf text values only. Never translate keys or restructure the locale tree.
- Only translate missing target-language leaf values unless the user explicitly asks to retranslate or overwrite existing strings.
- Preserve source key order when rebuilding target locale files.
- Remove keys from target locale files when those keys no longer exist in the source file, unless the project intentionally keeps compatibility aliases.
- Preserve placeholders, HTML, ICU fragments, template fragments, Markdown links, inline code, brand names, product names, abbreviations, and glossary terms.
- Do not wire translation sync into CI or build steps unless the user explicitly asks.

## Translation Safety

Protect these patterns before translating and restore them after translation:

- `{name}` / `{count}` / `{price}` style placeholders
- `{{ name }}` template placeholders
- ICU-like fragments such as `{count, plural, ...}`
- HTML tags such as `<strong>` or `<br>`
- Markdown links or inline code
- Brand and product glossary terms

If the repository has a glossary, respect it. If there is no glossary and key terminology appears frequently, propose one.

## Manual Sync Workflow

1. Confirm target languages unless they are already explicit.
2. Determine the source locale file.
3. If the source locale was not specified, locate a Chinese source locale such as `zh-CN.json` or `zh_CN.json`.
4. Stop and ask the user if no clear source locale can be identified.
5. Flatten nested locale objects into ordered key paths.
6. Compare the source locale against each target locale.
7. Translate only missing leaf values unless overwrite or retranslation was requested.
8. Rebuild target locale files using the exact source key order.
9. Summarize added, removed, and risky strings, including any strings that need manual review.

## Expected Output

For manual translation sync tasks, provide:

- Updated target locale files.
- A concise summary of added, changed, and removed keys.
- Any untranslated or risky strings that need manual review.

For workflow design tasks, provide:

- A local script design or implementation plan.
- Recommended cache strategy.
- Recommended package script names such as `i18n:sync` and `i18n:check`.

## Suggested Scripts

New projects may expose these scripts when locale tooling exists:

- `i18n:sync`
- `i18n:check`
